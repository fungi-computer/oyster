---
title: Agent quick start
description:
  Hand this guide to a coding agent to set up a local Oyster, install an App,
  connect over MCP, add Git and deploy.
---

You are an agent setting up Oyster for a person. Follow these steps in order.
Run every command exactly as written, from the directory each step names.
Compare its output with the expected output before you go on. When a step fails,
read the "If it fails" notes under it before trying anything else.

## What Oyster is

- Oyster hosts Apps on one Cloudflare Worker, or on celld, a Workers-compatible
  runtime you host yourself.
- Each App is an immutable Release built from an exact git commit. Its backend
  runs in its own Durable Object with its own SQLite, and it gets only the
  bindings it declares.
- People use Apps in a browser. Agents call the same App methods over HTTP or
  through one MCP endpoint, `/mcp`.

## 1. Check prerequisites

You need Node 24.20.0, pnpm 11.24.0, Git and curl. You do not need a Cloudflare
account until step 8, and you never need Docker for these steps.

```sh
node --version
pnpm --version
git --version
```

Expected output: `v24.20.0`, then `11.24.0`, then any `git version 2.x` line.

If it fails:

- Wrong Node: install 24.20.0 with your version manager, for example
  `mise use node@24.20.0` or `nvm install 24.20.0`.
- Wrong pnpm: run `corepack enable` and then
  `corepack prepare pnpm@11.24.0 --activate`.

## 2. Get the code

Oyster is not on npm yet. `npm install @fungi.computer/oyster` and
`npm create fungi-app` do not work. Oyster's source lives in the Fungi
repository, a pnpm monorepo, and you work from a checkout of it. Ask the person
for its git URL if they have not given you one.

```sh
git clone <repository-url> fungi
cd fungi
pnpm install --frozen-lockfile
```

Expected output: pnpm ends with a `Done in …` line. Warnings starting
`Failed to create bin at …fungi-local-auth` are harmless.

Every later command runs from this `fungi` directory, the repository root,
unless the step says otherwise.

If it fails:

- `ERR_PNPM_OUTDATED_LOCKFILE`: you are not on the commit the person gave you.
  Run `git status` and check out that commit; never drop `--frozen-lockfile`.

## 3. Build Oyster

```sh
pnpm turbo:run run build --filter=@fungi.computer/oyster...
```

Expected output: a Turbo summary ending in `Tasks: N successful, N total`, with
no failed tasks. The first build takes a few minutes.

If it fails:

- Read the first error, not the last. A failing dependency package means the
  checkout is incomplete; rerun `pnpm install --frozen-lockfile` and build
  again.

## 4. Run a local Oyster

This runs `packages/oyster/examples/standalone`, a complete single-owner Oyster,
under `wrangler dev` on your machine. Choose an owner key and keep this terminal
open:

```sh
export OYSTER_OWNER_KEY=$(openssl rand -hex 24)
export OYSTER_URL=http://127.0.0.1:8787
mkdir -p .botanical
echo "$OYSTER_OWNER_KEY" > .botanical/oyster-owner-key
cd packages/oyster/examples/standalone
npx wrangler dev --local --ip 127.0.0.1 --port 8787 \
  --var OYSTER_OWNER_KEY:$OYSTER_OWNER_KEY --var OYSTER_ORIGIN:$OYSTER_URL
```

`npx wrangler` runs the Wrangler version this package pins, which can differ
from the repository root's. Expected output: a bindings table listing
`env.MCP (OysterMcp)`, `env.REGISTRY (OysterRegistry)`,
`env.INSTANCES (OysterInstance)`, `env.RELEASES (oyster-releases)` and
`env.LOADER`, then `Ready on http://127.0.0.1:8787`.

Keep it running. Open a second terminal in the repository root, set the same two
variables there, and check that Oyster answers:

```sh
export OYSTER_OWNER_KEY=$(cat .botanical/oyster-owner-key)
export OYSTER_URL=http://127.0.0.1:8787
curl -s -o /dev/null -w '%{http_code}\n' $OYSTER_URL/login
curl -s -o /dev/null -w '%{http_code}\n' $OYSTER_URL/api/installations
curl -s -H "Authorization: Bearer $OYSTER_OWNER_KEY" $OYSTER_URL/api/installations
```

Expected output: `200`, then `401` (no key), then `[]` (no Apps installed yet).

If it fails:

- `Address already in use`: another process holds port 8787. Pick another port
  and use it in both `--port` and `OYSTER_URL`.
- `curl` prints `000`: the server is not ready yet. Wait for the `Ready on`
  line.
- `401` with the key: the two terminals hold different keys. Set
  `OYSTER_OWNER_KEY` from `.botanical/oyster-owner-key` in both.
- An agent runtime that cannot keep a process in the foreground starts the same
  command in the background with its output in a log, then waits until the
  `/login` check prints `200`:

  ```sh
  npx wrangler dev --local --ip 127.0.0.1 --port 8787 \
    --var OYSTER_OWNER_KEY:$OYSTER_OWNER_KEY --var OYSTER_ORIGIN:$OYSTER_URL \
    > ../../../../.botanical/oyster-dev.log 2>&1 &
  ```

To stop the server, press Ctrl-C in its terminal. A background server runs as
several processes (`npm exec`, `wrangler.js` and `workerd`); stop them all by
ending `wrangler.js`, then check that `/login` prints `000`:

```sh
pkill -f 'wrangler[.]js dev .*--port 8787'
```

## 5. Add an App and call it

`packages/oyster/examples/install-notes.ts` builds the Notes example App
(`packages/oyster/examples/notes-app`) from the checkout's current commit and
installs it as installation `notes`:

```sh
cd packages/oyster
pnpm exec tsx examples/install-notes.ts
cd ../..
```

Expected output, after about a minute: one line starting
`installed notes: 201 {"installationId":"notes",` and containing
`"status":"enabled"`.

Call its backend methods over HTTP, like any script or agent can:

```sh
curl -s -X POST -H "Authorization: Bearer $OYSTER_OWNER_KEY" \
  -H 'content-type: application/json' -d '{"text":"hello from my agent"}' \
  $OYSTER_URL/apps/notes/methods/saveNote
curl -s -X POST -H "Authorization: Bearer $OYSTER_OWNER_KEY" \
  -H 'content-type: application/json' -d '{}' \
  $OYSTER_URL/apps/notes/methods/readNote
```

Expected output: `{"saved":true}`, then `{"text":"hello from my agent"}`.

A person can open `$OYSTER_URL/login`, sign in with the owner key, and open
Notes from the installation list at `$OYSTER_URL/`.

If it fails:

- `Set OYSTER_URL and OYSTER_OWNER_KEY`: export both variables in this terminal.
- `Install refused (409): {"error":"installation_exists"}`: Notes is already
  installed. Go on to the method calls.
- `fetch failed` or `ECONNREFUSED`: the server from step 4 is not running.
- The build reads committed files only. To install your own edits to Notes,
  commit them first.

## 6. Connect over MCP

`/mcp` serves every installed App to MCP clients through one `execute` tool, in
which each App is `env.<APP>`. The owner key signs in. For Claude Code:

```sh
claude mcp add --transport http oyster "$OYSTER_URL/mcp" \
  --header "Authorization: Bearer $OYSTER_OWNER_KEY"
```

In that client, `execute` with the code `return await env.NOTES.readNote({})`
returns `{"text":"hello from my agent"}`.

To check `/mcp` without an MCP client, open a session and list its tools:

```sh
MCP=(-H "Authorization: Bearer $OYSTER_OWNER_KEY" -H 'content-type: application/json' -H 'accept: application/json, text/event-stream')
SESSION=$(curl -s "${MCP[@]}" -D - -o /dev/null \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}' \
  $OYSTER_URL/mcp | grep -i '^mcp-session-id' | cut -d' ' -f2 | tr -d '\r')
curl -s "${MCP[@]}" -H "mcp-session-id: $SESSION" -H 'mcp-protocol-version: 2025-11-25' \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}' $OYSTER_URL/mcp
curl -s "${MCP[@]}" -H "mcp-session-id: $SESSION" -H 'mcp-protocol-version: 2025-11-25' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"execute","arguments":{"code":"return await env.NOTES.readNote({})"}}}' \
  $OYSTER_URL/mcp
```

Expected output: the last command prints an `event: message` block whose `data:`
line contains `"isError":false` and `{\"text\":\"hello from my agent\"}`.

If it fails:

- `SESSION` is empty: the `initialize` call was refused. Check the key as in
  step 4.
- Named keys for each agent (`POST /api/keys`) come with the Git worker in
  step 7. The plain standalone Worker answers `404` there.

## 7. Add Git

`packages/oyster/examples/git` is the same Oyster with the git door: people and
agents `clone`, `fetch` and `push` App repositories with ordinary `git` at
`/git/<installation>/<repo>.git`. Repositories live in Cloudflare Artifacts,
which `wrangler dev` cannot emulate. This check runs that exact Worker on
workerd against a local Artifacts stand-in serving real bare repositories. Stop
the step 4 server as step 4 describes, or leave it running; this check picks its
own free port.

```sh
pnpm --filter @fungi.computer/oyster test:git-door
```

Expected output, within a minute:
`PASS examples/git on workerd: owner git push, agent push refused by App policy, clone, onGitPush delivered`.

Compared with `examples/standalone`, `examples/git/worker.ts` adds:

- `oysterWorkerGit(env)` as `host.git`, which mounts the git door;
- `ownerOrKeyAuth`, so the owner key and named keys sign in to git;
- `gitAdminRoutes`, which serves `/api/keys` and `/api/webhooks`;
- `OysterGitInstance` as `OysterInstance`, which hands Apps `env.GIT` and
  `env.EVENTS`;
- the `ARTIFACTS` binding and the `KEYS` and `WEBHOOKS` Durable Objects in its
  `wrangler.jsonc`.

With the Git worker deployed, give each agent its own key:

```sh
curl -s -X POST -H "Authorization: Bearer $OYSTER_OWNER_KEY" \
  -H 'content-type: application/json' \
  -d '{"name":"morel","grants":[{"capability":"apps.use","targets":{"kind":"all"}}]}' \
  $OYSTER_URL/api/keys
```

Expected output: JSON with a `plaintext` field starting `oyk_`. Oyster shows it
once; that key signs in to `git` and to `/mcp`.

If it fails:

- `git: command not found`: the check drives the real `git` client; install Git.
- The check prints the Worker's log before its error. Read the first `Error`
  line in it.

## 8. Deploy to Cloudflare Workers

This step needs a Cloudflare account on Workers Paid; Git also needs Artifacts
enabled on it. Ask the person before you deploy anything.

For the plain Oyster, edit `packages/oyster/examples/standalone/wrangler.jsonc`:
set `vars.OYSTER_ORIGIN` to the Worker's address
(`https://oyster.<your-subdomain>.workers.dev`, or a custom domain), and choose
an R2 bucket name. Then:

```sh
cd packages/oyster/examples/standalone
npx wrangler login
npx wrangler r2 bucket create oyster-releases
printf '%s' "$OYSTER_OWNER_KEY" | npx wrangler secret put OYSTER_OWNER_KEY
npx wrangler deploy
```

Expected output: `wrangler deploy` prints the deployed `https://` URL. Then
install Notes on it exactly as in step 5, with `OYSTER_URL` set to the deployed
address.

For Git, deploy from `packages/oyster/examples/git` the same way; its
`wrangler.jsonc` also names the Artifacts namespace `oyster`.

If it fails:

- `R2 bucket … already exists`: use that bucket, or pick a new name and put it
  in `wrangler.jsonc`.
- A secret prompt on stdin: pipe the key as shown; never type it into a log.
- Bindings or migrations refused: deploy the matching `wrangler.jsonc` unchanged
  except for `vars` and the bucket name.
